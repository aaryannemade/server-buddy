# Security Design and Threat Model (Protocol v1)

## Assets

- Per-node keys and derived LMK/MIC keys (radio confidentiality/integrity).
- HA credential and hub TLS private key (control of the hub).
- Integrity of states/events delivered to HA (automations act on them).

## Attacker model

| Attacker | In scope | Notes |
| --- | --- | --- |
| Passive radio listener | yes | Learns only metadata (MACs, timing, key ID). |
| Active radio attacker (inject, replay, spoof MAC) | yes | Must not create entities, forge states/events, or replay events. |
| LAN attacker (sniff, MITM, spoof mDNS, race commissioning) | partial | Authenticated sessions are in scope; first-claim race protection is deferred to Phase 8. |
| Physical access to a node | partial | Exposes only that node's key. |
| Physical access to the hub | no | Owner-equivalent until flash/NVS encryption (Phase 8). |
| RF jamming / radio DoS | no | Detected via availability, not prevented. |

## Radio keys

- **PMK**: fixed, documented, non-secret project constant
  (`ServerBuddyPMKv1`). ESP-NOW needs the same PMK on both peers and the hub
  has one PMK for all peers, so it cannot be a per-node secret.
- **Node key** (`K_node`, 16 random bytes): generated by the hub when the user
  adds a node in HA, shown once for the node's ESPHome `secrets.yaml`, stored
  in hub NVS.
- **Key ID**: `trunc4(HMAC-SHA256(K_node, "sb-v1 id"))`, sent in the clear so
  the hub can select the key without trial verification.
- **Session keys**: `OKM = HKDF-SHA256(ikm=K_node, salt=node_nonce||hub_nonce,
  info="sb-v1 keys"||node_mac||hub_mac||epoch, L=32)`;
  `LMK = OKM[0:16]` (ESP-NOW CCMP, confidentiality),
  `K_mic = OKM[16:32]` (application MIC, authenticity).
- **Application MIC**: every non-pairing frame ends with
  `trunc8(HMAC-SHA256(K_mic, "sb-v1 mic"||dir||frame_before_mic))`, `dir` = 0
  node→hub, 1 hub→node. The MIC is verified before decoding. It does not rely
  on ESP-NOW rejecting plaintext from an encrypted peer, which ESP-IDF does
  not guarantee or report.
- Encrypted-peer limit: C6 built with `CONFIG_ESP_WIFI_ESPNOW_MAX_ENCRYPT_NUM=17`;
  the hub refuses an 18th node and never falls back to plaintext.

## Pairing (mutual proof of `K_node`)

Pairing is **targeted**. Adding a node in authenticated HA opens a 120 s window
for that new key. Re-pairing an enrolled node requires an explicit HA action
for that node. Requests for any other key ID are ignored, so replayed requests
cannot disturb running nodes. Only one pairing is in progress at a time.

1. The node uses its configured fixed channel (same as the hub's). It
   broadcasts `PAIR_REQUEST{key_id, node_mac, node_nonce[16], tag}` with
   `tag = trunc16(HMAC(K_node, "sb-v1 req"||frame_before_tag))`, retrying every
   500 ms for up to 30 s.
2. The hub drops the request unless `node_mac` equals the ESP-NOW source MAC
   and the tag verifies. It picks `hub_nonce[16]` and the next epoch, and
   replies unicast (unencrypted) with `PAIR_RESPONSE{status, hub_mac,
   hub_nonce, channel, epoch, tag}`, where the tag covers
   `"sb-v1 resp"||node_nonce||frame_before_tag`. The node verifies it, which
   proves the hub knows `K_node` and binds the response to this request.
3. Both sides derive the session keys. The hub installs the peer (by source
   MAC) with the new LMK as **pending**. It becomes active when a valid
   `HELLO` under the new keys arrives within 10 s; otherwise the hub restores
   the previous peer state.
4. The node writes hub MAC, keys and epoch to NVS **only after** the hub ACKs
   that HELLO. If the ACK is lost, the node keeps its old state and retries
   pairing.
5. The epoch is u8 (1..255, wrapping to 1) and carried in every header. A new
   epoch resets the hub's replay counters for that node. The hub also keeps a
   persistent u32 **generation** per node, incremented on every pairing, for
   external identifiers.

Pairing frames cannot use ESP-NOW encryption (broadcast); their integrity
comes from the HMAC tags. All tag/MIC comparisons are constant time.

## Replay protection

- The node keeps a **boot counter** in NVS, incremented on every cold boot
  (not on deep-sleep wake). Its **sequence** lives in RTC memory and resets to
  0 per boot.
- Every enrolled frame carries `(epoch, boot, seq)` covered by the MIC.
- The hub accepts `boot > last_boot`, or `boot == last_boot && seq > last_seq`.
  An equal `(boot, seq)` is a retry: re-ACK, do not reprocess. Older frames
  are dropped.
- **Persist before acting**: when `boot > last_boot`, the hub durably writes
  the new `last_boot` before processing or ACKing the frame. If the write
  fails, the frame is dropped.
- `last_seq` is kept in RAM. After a hub restart it is unknown, so a frame
  with `boot == last_boot` gets `ACK{status=NEW_BOOT}` (MIC-protected). The
  node increments its boot counter and resends.
- **Hub→node frames**: the node accepts an ACK only if its MIC verifies,
  `epoch` matches, and `(acked_boot, acked_seq)` equals the frame the node is
  currently waiting on. Anything else is ignored.
- **Events** carry `(origin_boot, event_no)`, which is fixed when the event is
  created and kept across retries, NEW_BOOT resends and next-wake resends. The
  hub drops repeats (remembering the last 32 per node). The HA event ID is
  `hub_id:node_id:generation:origin_boot:event_no`.

## Home Assistant link

- The P4 generates an ECDSA P-256 key and self-signed certificate on first
  boot. The API is TLS-only (WSS/HTTPS).
- **Initial commissioning (Phase 5 local mode)**: while no HA credential
  exists, the first client on the local network may claim the hub through the
  HA config flow. The hub issues a 256-bit random token to that TLS session and
  stores only `SHA-256(token)`. No button, one-time code, or fingerprint check
  is required in this mode.
- This intentionally accepts a first-claim race from another device on the
  same LAN. It is suitable for the current trusted local deployment, but does
  not satisfy the production security gate.
- Every session uses the pinned fingerprint plus the token. HA can rotate the
  token over the authenticated channel.
- Phase 8 adds physical-presence or equivalent owner proof, fingerprint
  verification, claim-race handling, and a credential-revocation recovery
  path before production release.

## Lifecycle

| Event | Action |
| --- | --- |
| Remove node in HA | Hub deletes the peer, key and counters; the node's frames are rejected. |
| Lost or compromised node key | Remove the node, add it again (new key), reflash the node. |
| HA credentials lost | Development recovery explicitly erases the HA credential; a protected owner-recovery flow is deferred to Phase 8. |
| Hub factory reset | Explicit serial/flashing-tool reset erases hub NVS. A physical recovery action is deferred to Phase 8. |
| Node factory reset or reflash | Boot counter restarts; HA re-pair action (new epoch). |

## Insecure development mode

Compile-time `SB_INSECURE_DEV=1` on hub and node disables ESP-NOW LMK
encryption (plaintext on air). Pairing tags and MICs stay mandatory. The hub
logs a warning at boot and reports the mode in diagnostics, and the HA
integration raises a repair issue. This mode can never pass a release gate.

## Deferred to Phase 8

Physical-presence commissioning, first-claim race protection, credential
revocation/recovery, secure boot, flash and NVS encryption, signed OTA, and key
rotation without re-pairing.
